### Catalog caching and runtime behavior

Catalog JSON moved out of versioned asset caching into a `freshness` data group (5-second network timeout, one cached catalog, 30-day maximum age, query-insensitive cache lookup). Images remain versioned assets. Cache-busted HTTP requests avoid stale browser HTTP responses. Visible clients recheck at 15-minute intervals and on return after that interval, without overlapping requests or replacing valid in-memory data on malformed/unavailable responses. Initial requests have a bounded 20-second failure/retry path.

The [Angular data-group configuration](https://angular.dev/ecosystem/service-workers/config) supports data updates independently of application asset versions. Existing installations must adopt this initial client/service-worker change; later valid catalog data does not need another application feature release. Offline fallback applies to a cached valid response when the network is unavailable/too slow. This is not offline audio support or an offline-install certification. An HTTP error response is handled by the app's initial error/retry or preservation of an already loaded catalog; it is not claimed to have the same fallback behavior as a disconnected network.

### Cold HTTP 503 investigation

Finding: **absence of a cached catalog is not the sole explanation**. The already-recorded Milestone 4 browser sequence showed cached catalog data surviving connection loss while a responding HTTP 503 caused cold-start Retry. Reinspection of the pinned Angular 21.2.25 worker's `DataGroup.handleFetchWithFreshness` confirms the distinction: only undefined/rejected/timed-out network results enter cache lookup; a completed 503 response is returned. Its unsuccessful response is not cached, so the previous valid cache may still exist but is not used for that request. This is consistent with Angular's documented [freshness strategy](https://angular.dev/ecosystem/service-workers/config#strategy).

Consequently, it is expected worker policy but a real **application cold-start fallback limitation even with a valid cache**, rather than proof that the browser had no cache. Already-open clients retain their valid in-memory catalog on background failure, as preserved M3 tests confirm. Retry can recover when the origin responds normally. No cache/persistence architecture or RSS refresh behavior was changed. A dedicated last-known-good HTTP-error fallback remains a separately scoped design decision, not an unreported M5 implementation. The fresh native-browser replay prepared here remains unverified.
